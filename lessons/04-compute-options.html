#4 実行環境の選び方

Compute Engine / GKE / Cloud Run / Cloud Run functions / App Engine の違いを、「自分で管理する範囲」で整理する

この回のゴール
  • 5つの実行環境で、自分で用意・管理するものと Google が管理するものの違いを説明できる
  • 要件（既存システムの移行、HTTP の API、イベント処理、Kubernetes など）から実行環境を選べる
  • Compute Engine のマシンタイプ、Spot VM、マネージド インスタンス グループ（MIG）を説明できる
  • GKE の Autopilot モードと Standard モード、App Engine のスタンダード環境とフレキシブル環境の違いを説明できる
  • VM を作成・停止・削除し、停止中も料金がかかるものを説明できる

1. 全体像：どこまで自分で管理するか

GCP でアプリを動かす場所（実行環境）はいくつもあります。違いは、自分で用意・管理するものと、Google に任せるものの境目です。自分で管理する範囲が広いほど自由に設定できますが、手間と責任も増えます。

台数の増減MIG で自動スケーリングを設定する（2-1）Pod とノードを自動で増減できるリクエストなどに応じて自動自動

向いているもの既存システムの移行、OS の設定が必要なもの多数のコンテナを Kubernetes で運用したいWeb アプリ、API、バッチイベントに反応する小さな処理

2. それぞれの実行環境

2-1. Compute Engine：VM（仮想マシン）

Compute Engine は、VM（公式ドキュメントでは「インスタンス」とも呼ぶ）を作るサービスです。OS から上はすべて自分で管理します。手間はかかりますが、オンプレミスのサーバーと同じ感覚で何でも動かせます。

マシンタイプ

VM の CPU とメモリの大きさはマシンタイプで決めます。マシンタイプは、マシン ファミリー（汎用、コンピューティング最適化など）→ マシンシリーズ（E2、N2、C3 など）→ マシンタイプ（e2-standard-2 など）の順に分類されています。

  • e2-micro、e2-small、e2-medium は共有コアのマシンタイプ。物理コアを時間で分け合う小さな VM で、短い時間なら CPU をフルに使える（バースト）。たとえば e2-micro は、2つの vCPU をそれぞれ 12.5% の時間ずつ使える
  • 決まった大きさで足りなければ、vCPU とメモリを指定したカスタム マシンタイプも作れる

Spot VM：安いが、いつ止められてもよい処理向け

Spot VM は、Compute Engine の余っている容量を使う VM です。通常の VM より大幅に安く（多くのマシンタイプで最大 91% 引き）なりますが、Google が容量を必要とするといつでも停止または削除（プリエンプト）されます。

  • 途中で止まってもやり直せる処理（バッチ処理、ステートレスなアプリなど）に向いている。止まると困る処理には使わない
  • 以前はプリエンプティブル VM という仕組みがあった。Spot VM はその新しい版で、プリエンプティブル VM の「最長 24 時間で止まる」という制限がない。公式ドキュメントでは Spot VM を使うよう推奨している

マネージド インスタンス グループ（MIG）：同じ VM をまとめて運用する

同じ構成の VM を複数台まとめて扱う仕組みです。VM の設計図となるインスタンス テンプレートから、VM を自動で作ります。

  • ゾーン MIG は1つのゾーンに、リージョン MIG は複数のゾーンに VM を作る。ゾーンの障害に備えるならリージョン MIG
  • MIG に向いているのは、どの VM が処理しても結果が同じステートレスなもの（Web サーバーなど）
  • 構成の違う VM をまとめるだけの非マネージド インスタンス グループもあるが、自動スケーリングや自動修復は使えない

停止しても、料金がかかるもの

VM を停止すると、状態は TERMINATED になり、vCPU とメモリの料金はかかりません。ただし、ディスク、スナップショット、VM に付けたままの外部 IP アドレスは、停止中も課金されます。使わない VM は、停止ではなく削除します。

何も指定しないと、VM は編集者ロールを持つサービスアカウントで動くことがある

VM を作るときにサービスアカウントを指定しないと、Compute Engine は、デフォルトのサービスアカウントを VM に関連付けます（#2 の 6-3）。組織のないプロジェクトなどでは、このサービスアカウントにプロジェクトの編集者ロールが自動で付与されています。この学習用プロジェクトでも、Compute Engine API を有効にした時点でそうなっていました（ハンズオンの手順1で確認します）。本番では、アプリごとに専用のサービスアカウントを作って関連付けます。

2-2. GKE（Google Kubernetes Engine）：Kubernetes

GKE は、コンテナを動かすための仕組みである Kubernetes を、Google が管理する形で使えるサービスです。Kubernetes の頭脳にあたるコントロール プレーンは Google が管理し、コンテナはノード（中身は Compute Engine の VM）の上で動きます。GKE には2つのモードがあります。

Autopilot モード（推奨）Standard モード
ノードGoogle が管理する。台数やサイズを考えなくてよい自分で管理する（ノードプールのマシンタイプや台数を決める）
課金主に Pod が要求したリソース（CPU・メモリなど）ノードの VM（Compute Engine の料金）
向いているものほとんどの本番ワークロード特別な権限や、ノードの細かい制御が必要なもの
  • どちらのモードも、クラスタ1つにつき1時間 $0.10 のクラスタ管理手数料がかかる。請求先アカウントごとに毎月 $74.40 の無料枠（Autopilot クラスタかゾーンの Standard クラスタ1つ分）がある
  • Kubernetes 自体の知識（Pod、Deployment、Service など）が必要になる。チームに経験者がいるか、学ぶ時間があるかも判断材料

2-3. Cloud Run：コンテナを渡すだけで動く

Cloud Run は、コンテナを渡すと、サーバーの用意や台数の増減を Google がすべて行うサービスです。コンテナ イメージを作らなくても、Go、Node.js、Python、Java などはソースコードからデプロイできます（コンテナは自動でビルドされる）。

種類何をするか例
サービスHTTP リクエストを受けて応答する。*.run.app の URL が付くWeb アプリ、API
ジョブ手動またはスケジュールで実行し、終わったら止まる夜間バッチ、データ移行
ワーカープールリクエストを受けずに、常に動き続けるPub/Sub などのキューからメッセージを取り出して処理する
  • リクエストがなければインスタンスは0 台まで減る（ゼロへのスケーリング）。最初のリクエストは起動を待つので少し遅くなる。避けたいなら最小インスタンス数を設定する（その分の料金がかかる）
  • 新しいリビジョン（版）に少しずつトラフィックを移したり、前のリビジョンに戻したりできる
  • #3 で扱ったとおり、Cloud Run は VPC ネットワークの外で動く。VPC の中のリソースにつなぐには設定が必要

実際に動かすのは #5 Cloud Run ハンズオンで行います。

2-4. Cloud Run functions：関数を渡すだけで動く

Cloud Run functions は、関数のコードだけを書いて動かすサービスです。デプロイすると、関数は自動でコンテナにビルドされ、Cloud Run サービスとして動きます。

  • HTTP リクエストのほか、イベント（Cloud Storage へのファイルのアップロード、Pub/Sub のメッセージなど）をきっかけに動かせる。イベントは Eventarc で受け取る
  • 以前の名前は Cloud Functions。今の Cloud Run functions は旧称「Cloud Functions（第 2 世代）」で、旧称「Cloud Functions（第 1 世代）」は「Cloud Run functions（第 1 世代）」になった。試験や既存の資料では古い名前で出てくることがある

2-5. App Engine：以前からあるアプリの実行環境

App Engine は、コードをデプロイするとアプリとして動かしてくれる、以前からあるサービスです。公式ドキュメントでは、新しく使う場合は App Engine の代わりに Cloud Run を使うよう推奨しています。ただし、既存のシステムで使われていることがあり、ACE でも出題されるので、2つの環境の違いは押さえておきます。

スタンダード環境フレキシブル環境
動く場所Google が用意した言語ごとのランタイム（サンドボックス）Compute Engine の VM 上の Docker コンテナ
起動・デプロイ数秒数分
0 台まで減るか減る減らない（最低1インスタンス）
向いているもの急なアクセスの増加、無料や低コストで動かしたいもの独自のランタイムや、ネイティブ コードを含むライブラリが必要なもの
  • App Engine のアプリのリージョンは、作った後に変更できない

3. 選び方

実際には、次の順に質問していくと整理しやすくなります。公式の決定木ではなく、ここまでの内容を整理したものです。

  • Q1：コンテナにできないもの（特定の OS の設定が必要、コンテナでは動かせない市販ソフト、OS ごとのライセンスなど）は Compute Engine。既存のサーバーをそのまま移す（リフト＆シフト）場合もここ
  • Q2：Kubernetes の知識と運用の体制があるか。ないなら、Kubernetes を選ぶだけで運用の負担が大きくなる
  • Q3：処理が関数1つで済むなら Cloud Run functions。複数のエンドポイントを持つ API なら Cloud Run のほうが扱いやすい
ACE のポイント
  • 問題文の言葉から選ぶ：「既存のアプリをそのまま移行」「OS へのアクセスが必要」→ Compute Engine。「ステートレスなコンテナ」「トラフィックがないときは費用をかけない」→ Cloud Run。「Cloud Storage にファイルがアップロードされたら処理」→ Cloud Run functions（古い名前の Cloud Functions で出ることもある）。「Kubernetes」「ノードを管理したくない」→ GKE Autopilot
  • 「途中で止まってもよいバッチを安く」→ Spot VM（またはプリエンプティブル VM）。止まると困る処理には使わない
  • 「負荷に応じて VM を増減」「故障した VM を自動で置き換え」→ インスタンス テンプレート＋マネージド インスタンス グループ（自動スケーリング、ヘルスチェックによる自動修復）。ゾーン障害にも備えるならリージョン MIG
  • App Engine：「0 台まで減らしたい」「急なアクセス増加」→ スタンダード環境。「独自のランタイム」「Docker」→ フレキシブル環境。リージョンは後から変えられない
  • VM を停止しても、ディスクと外部 IP アドレスの料金はかかる

4. テックリードの視点

参画したら確認したいこと
  • どの実行環境を使っているか。それを選んだ理由は何か（理由がわかると、変更の判断がしやすい）
  • VM で動いているものは、OS の更新やセキュリティ パッチを誰がいつ行っているか
  • バッチ処理はどこで動いているか（VM の cron か、Cloud Run ジョブ＋Cloud Scheduler か）
  • VM や Cloud Run に、どのサービスアカウントを関連付けているか。デフォルトのサービスアカウントのままになっていないか
  • 最小インスタンス数、GKE のクラスタ数など、使っていなくてもかかる費用がないか
  • オフショアチームへの説明：「どこまでが自分たちの責任か」を図1の形で示すと伝わりやすい。たとえば Compute Engine なら、OS の更新も自分たちの仕事になる
  • よくある誤解：「Cloud Run は小さなアプリ向け」と思われがち。実際は、Web アプリや API の多くは Cloud Run で動かせる。逆に、「とりあえず Kubernetes」で GKE を選ぶと、運用の負担が大きくなる
  • 設計レビューの観点：VM を選んでいるなら、コンテナにできない理由があるか。VM を1台ずつ手で作っていないか（インスタンス テンプレートと MIG、または Terraform などで再現できるか）

5. ハンズオン：Compute Engine の VM を作って、停止して、削除する

学習用の configuration を有効にしたターミナルで実行します（export CLOUDSDK_ACTIVE_CONFIG_NAME=study）。一番自分で管理する範囲が広い Compute Engine を触って、何が自分の管理になるのかを確かめます。Cloud Run は #5 で扱います。

料金について：us-central1 の e2-micro と、30 GB までの標準永続ディスク（pd-standard）は、Compute Engine の無料枠の対象です（無料枠は請求先アカウント単位で、1か月に e2-micro 1台分の時間まで）。無料枠を使い切っていた場合でも、e2-micro を1時間動かして数円程度です（目安。正確な金額は公式の料金ページで確認してください）。外部 IP アドレスは付けません。最後に VM を削除します。

手順1. 作る前に観察する（読み取りのみ）

# 小さめのマシンタイプ（CPUS と MEMORY_GB を比べる）
gcloud compute machine-types list --zones=us-central1-a \
  --filter="name:(e2-micro e2-small e2-medium e2-standard-2)"

# サービスアカウントの一覧（Compute Engine のデフォルトのサービスアカウントがある）
gcloud iam service-accounts list

# デフォルトのサービスアカウントに付いているロール
gcloud projects get-iam-policy $(gcloud config get-value project) \
  --flatten="bindings[].members" \
  --filter="bindings.members~compute@developer" \
  --format="table(bindings.role)"

デフォルトのサービスアカウントは、#3 で Compute Engine API を有効にしたときに自動で作られています。3つ目のコマンドで roles/editor（編集者）が表示されれば、2-1 の注意点のとおりです。

手順2. VM を作る

gcloud compute instances create study-vm \
  --zone=us-central1-a \
  --machine-type=e2-micro \
  --image-family=debian-12 \
  --image-project=debian-cloud \
  --boot-disk-type=pd-standard \
  --boot-disk-size=10GB \
  --no-address \
  --no-service-account \
  --no-scopes
指定意味
--zoneVM はゾーンのリソース。無料枠の対象の us-central1 のゾーンを使う
--image-family
--image-project		OS のイメージ。debian-cloud プロジェクトにある Debian 12 の最新版を使う
--boot-disk-type
--boot-disk-size		ブートディスク。無料枠の対象の標準永続ディスクを 10 GB で作る
--no-address外部 IP アドレスを付けない（#3 の5節）
--no-service-account
--no-scopes		サービスアカウントを関連付けない。指定しないと、編集者ロールを持つデフォルトのサービスアカウントを関連付けることになる

ネットワークを指定していないので、デフォルト ネットワークの us-central1 のサブネットが使われます。ディスクのサイズが小さいと性能が下がる、という警告が出ることがありますが、学習用なので問題ありません。

手順3. 作ったものを確認する（読み取りのみ）

# VM の一覧（STATUS が RUNNING、EXTERNAL_IP が空のはず）
gcloud compute instances list

# VM の詳しい情報から、一部だけ表示する
gcloud compute instances describe study-vm --zone=us-central1-a \
  --format="yaml(status,machineType,networkInterfaces[0].networkIP,serviceAccounts,scheduling)"

# ブートディスクは、VM とは別のリソースとして作られている
gcloud compute disks list

手順4. IAP を通して SSH する

gcloud compute ssh study-vm --zone=us-central1-a --tunnel-through-iap
  • VM に外部 IP アドレスはありませんが、IAP による TCP 転送（#3 の5節）で SSH できます。デフォルト ネットワークの default-allow-ssh（送信元 0.0.0.0/0）が、IAP の範囲 35.235.240.0/20 からの接続も許可しています
  • 初めて使うときは SSH の鍵が作られ（パスフレーズを聞かれる）、公開鍵がプロジェクトのメタデータに登録されます

VM に入ったら、次を試して exit で抜けます。

# VM が自分の情報を知るためのメタデータ サーバー。どのゾーンで動いているかがわかる
curl -s -H "Metadata-Flavor: Google" \
  http://metadata.google.internal/computeMetadata/v1/instance/zone; echo

# インターネットには出られない（外部 IP アドレスも Cloud NAT もないため）。5秒で諦める
curl -m 5 -sI https://www.google.com || echo "つながらない"

exit

手順5. 停止する

gcloud compute instances stop study-vm --zone=us-central1-a

# STATUS が TERMINATED になる。ディスクは残っている
gcloud compute instances list
gcloud compute disks list

この状態では vCPU とメモリの料金はかかりませんが、ディスクの料金はかかり続けます（2-1）。

手順6. 片付ける

gcloud compute instances delete study-vm --zone=us-central1-a

# ブートディスクも一緒に消えたことを確認する（Listed 0 items.）
gcloud compute instances list
gcloud compute disks list

ブートディスクは、既定では VM を削除すると一緒に削除されます。

Q1. 手順1の3つ目のコマンドで、デフォルトのサービスアカウントには何のロールが付いていたでしょう？手順2で --no-service-account を付けたのはなぜでしょう？

答えを見る

roles/editor（編集者）です。サービスアカウントを指定せずに VM を作ると、このサービスアカウントを VM に関連付けることになり、VM の上で動くプログラムがプロジェクトのほとんどのリソースを変更できてしまいます。今回の VM は Google の API を使わないので、サービスアカウント自体を関連付けませんでした。

Q2. 手順4で、VM からインターネットにつながらなかったのはなぜでしょう？つなぐにはどうすればよいでしょう？

答えを見る

VM に外部 IP アドレスがなく、Cloud NAT もないからです。デフォルト ルートはあっても、それだけでは外に出られません（#3）。外部 IP アドレスを付けずに外に出るには、Cloud NAT を構成します。

Q3. 手順5で VM を停止した後も、料金がかかり続けるものは何でしょう？

答えを見る

ブートディスクです。外部 IP アドレスを付けていた場合は、それも課金されます。使わない VM は、停止ではなく削除します。

6. 確認テスト（ACE 形式）

問1. オンプレミスで動いている業務アプリを、できるだけ変更せずに Google Cloud に移行したいと考えています。アプリは特定の OS の設定と、OS 単位でライセンスされた市販のミドルウェアに依存しています。どの実行環境を選びますか。

  1. Cloud Run
  2. Compute Engine
  3. App Engine スタンダード環境
  4. Cloud Run functions
答えを見る

正解：B

OS の設定や OS 単位のライセンスに依存するアプリをそのまま移す（リフト＆シフト）なら、OS から自分で管理できる Compute Engine です。

  • A：コンテナにする必要があり、OS の設定やライセンスの条件を満たせない可能性があります
  • C：Google が用意したランタイムのサンドボックスで動くので、OS の設定はできません
  • D：関数として書き直す必要があり、「できるだけ変更せずに」に反します

問2. コンテナにしたステートレスな REST API を公開します。アクセスは日中に集中し、夜間はほとんどありません。運用の手間とコストをできるだけ小さくしたいと考えています。どうすればよいですか。

  1. GKE Standard クラスタを作り、ノードプールで自動スケーリングを設定する
  2. Compute Engine のマネージド インスタンス グループで自動スケーリングを設定する
  3. Cloud Run サービスにデプロイする
  4. App Engine フレキシブル環境にデプロイする
答えを見る

正解：C

Cloud Run は、リクエストに応じて自動で台数を増減し、リクエストがなければ 0 台まで減ります。サーバーの管理も不要です。

  • A：ノードの管理が必要で、クラスタ管理手数料もかかります
  • B：OS の管理が必要で、VM は 0 台まで減りません
  • D：フレキシブル環境は最低1インスタンスが動き続けます

問3. Cloud Storage のバケットに画像がアップロードされるたびに、サムネイル画像を作りたいと考えています。処理は短く、コードも少量です。サーバーの管理はしたくありません。どうすればよいですか。

  1. Compute Engine の VM で、バケットを1分ごとに確認する cron ジョブを動かす
  2. Cloud Storage のイベントをトリガーにする Cloud Run functions の関数を作る
  3. GKE Autopilot クラスタで、バケットを確認し続ける Pod を動かす
  4. App Engine スタンダード環境で、バケットを確認し続けるアプリを動かす
答えを見る

正解：B

Cloud Run functions は、Cloud Storage へのアップロードなどのイベントをきっかけに関数を実行できます。イベントがないときは費用もかかりません。

  • A、C、D：どれもバケットを定期的に確認し続ける作りで、処理がないときも動き続けます。A は VM の管理も必要です

問4. 毎晩、大量のデータを変換するバッチ処理を Compute Engine で実行しています。処理は途中で止まっても、最初からやり直せます。コストをできるだけ下げたいと考えています。どうすればよいですか。

  1. VM を Spot VM として作成する
  2. VM のマシンタイプを大きくして、処理時間を短くする
  3. VM を単一テナントノード上に作成する
  4. 処理が終わったら VM を停止し、外部 IP アドレスは付けたままにする
答えを見る

正解：A

Spot VM は、いつ停止されるかわからない代わりに、通常の VM より大幅に安くなります。やり直しができる（フォールト トレラントな）バッチ処理に向いています。

  • B：処理時間は短くなっても、単価が上がるので、コストが下がるとは限りません
  • C：単一テナントノードは、物理サーバーを専有するための仕組みで、コストは上がります
  • D：停止は正しい方向ですが、外部 IP アドレスは付けたままだと課金されます

問5. Compute Engine で動く Web アプリがあります。アクセスの増減に合わせて VM の台数を自動で調整し、応答しなくなった VM は自動で作り直したいと考えています。また、1つのゾーンで障害が起きても動き続けるようにしたいと考えています。どうすればよいですか。

  1. VM のスナップショットを1時間ごとに作成し、障害時に復元する
  2. インスタンス テンプレートを作成し、それを使うリージョン マネージド インスタンス グループを作成して、自動スケーリングとヘルスチェックによる自動修復を設定する
  3. インスタンス テンプレートを作成し、それを使うゾーン マネージド インスタンス グループを作成して、自動スケーリングを設定する
  4. 同じ構成の VM を3つのゾーンに手動で作成し、非マネージド インスタンス グループにまとめる
答えを見る

正解：B

台数の自動調整は自動スケーリング、VM の作り直しはヘルスチェックによる自動修復で実現します。リージョン MIG なら、VM が複数のゾーンに分散されます。

  • A：復元は手作業で、台数の自動調整もできません
  • C：ゾーン MIG は1つのゾーンだけなので、ゾーンの障害に耐えられません。自動修復も設定していません
  • D：非マネージド インスタンス グループでは、自動スケーリングも自動修復も使えません

問6. 社内では、数十個のマイクロサービスを Kubernetes のマニフェストで管理しています。これらを Google Cloud に移行したいのですが、ノードのサイズや台数の管理、ノードの更新はしたくありません。どうすればよいですか。

  1. GKE Standard クラスタを作成し、ノードプールを自分で設計する
  2. GKE Autopilot クラスタを作成し、既存のマニフェストでデプロイする
  3. マイクロサービスごとに Compute Engine の VM を作り、Kubernetes を自分でインストールする
  4. すべてのマイクロサービスを1つの App Engine スタンダード環境のアプリにまとめる
答えを見る

正解：B

Kubernetes のマニフェストをそのまま使え、ノードの管理を Google に任せられるのは GKE Autopilot です。

  • A：Standard モードでは、ノードの管理が自分の仕事になります
  • C：Kubernetes そのものの運用まで自分で行うことになり、要件と逆です
  • D：Kubernetes のマニフェストは使えず、大きな作り直しが必要です

まとめ

  • 実行環境の違いは「自分で管理する範囲」。Compute Engine（OS から上）→ GKE（コンテナと Kubernetes の設定）→ Cloud Run（コンテナ）→ Cloud Run functions（関数のコード）の順に、自分で管理するものが減る
  • コンテナにできないなら Compute Engine、Kubernetes が必要なら GKE（まず Autopilot）、イベントに反応する小さな処理なら Cloud Run functions、それ以外は Cloud Run
  • Compute Engine：マシンタイプ、Spot VM（安いが止められることがある）、インスタンス テンプレートとマネージド インスタンス グループ（自動スケーリング、自動修復、リージョン MIG）
  • VM を停止しても、ディスクと外部 IP アドレスは課金される。デフォルトのサービスアカウントには編集者ロールが付いていることがある
  • Cloud Run functions の以前の名前は Cloud Functions。App Engine は新しく使うなら Cloud Run が推奨。スタンダード環境は 0 台まで減り、フレキシブル環境は最低1インスタンス
