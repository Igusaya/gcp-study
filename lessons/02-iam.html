#2 IAM

「誰に・何を・どこで」許可するかの仕組みと、アプリに権限を与えるサービスアカウントを理解する

この回のゴール
  • IAM の3つの要素（プリンシパル・ロール・許可ポリシー）を説明できる
  • 基本ロール・事前定義ロール・カスタムロールの違いと使い分けを説明できる
  • 拒否ポリシーがいつ・どう効くかを説明できる
  • サービスアカウントの役割と、安全な使い方を説明できる
  • 最小権限の考え方で、ロールの付与を設計できる

1. IAM は「誰に・何を・どこで」

IAM（Identity and Access Management）は、誰に（プリンシパル）、何を（ロール）許可するかを、どこで（許可ポリシーを付けたリソース）有効にするかを決める仕組みです。

AWS 経験者が間違えやすいポイント AWS では、ポリシーを主にユーザーやロール（人やアプリの側）に付けます。GCP の許可ポリシーはリソースの側に付けます。「このプロジェクトでは、誰に、どのロールを与えるか」という書き方です。

2. プリンシパル（誰に）

許可ポリシーの中では、プリンシパルを「種類:識別子」の形で書きます。

種類書き方の例使いどころ
Google アカウントuser:alex@example.com個人。実務では直接付与せず、グループ経由にするのが基本
Google グループgroup:dev@example.comチーム単位の付与はこれ。メンバーの増減は、ポリシーを変えずにグループ側で管理できる
サービスアカウントserviceAccount:app@PROJECT_ID.iam.gserviceaccount.comアプリやワークロードの身元（項番5）
ドメインdomain:example.comGoogle Workspace / Cloud Identity のドメインに属する全員
認証済みの全ユーザーallAuthenticatedUsersGoogle アカウントでログインした人なら誰でも。社外の人も含む
全ユーザーallUsersインターネット上の誰でも（ログイン不要）。公開してよいものだけ

ほかに、社外の ID プロバイダの ID を使う Workforce Identity 連携・Workload Identity 連携のプリンシパル（principal://…）などもあります。

allUsers と allAuthenticatedUsers に注意 allAuthenticatedUsers は「自社の社員」ではなく、Google アカウントを持つ世界中の誰でもという意味です。バケットの情報漏えい事故の原因になりやすいので、付与する前に必ず確認しましょう。

基本ロールの新旧

基本ロールには、新しい3つと、IAM ができる前からある従来の基本ロール（legacy basic roles）の3つがあります。どちらも現在使えます。権限の数は新旧でほぼ同じです（2026-11 時点で確認した値）。

できること基本ロール従来の基本ロール権限の数
見るだけ読み取り（roles/reader）閲覧者（roles/viewer）約6,350
ほとんどのリソースの作成・変更・削除書き込み（roles/writer）編集者（roles/editor）約12,500
上に加えて、IAM（ロールの付与）や課金の設定管理者（roles/admin）オーナー（roles/owner）約14,200
  • 公式ドキュメントは、基本ロールを使うなら新しいほう（管理者・書き込み・読み取り）を勧めている。条件を付けられるなど、使える機能が多いため
  • 従来の基本ロールも現役。たとえば、プロジェクトを作った人には自動でオーナーが付与される（#1 のハンズオンで確認した roles/owner）
  • 管理者やオーナーでも、拒否ポリシーの作成や、Cloud Billing のお支払い情報の変更はできない
  • どちらにしても範囲が広いので、本番では基本ロールを原則使わないという方針は変わらない
ACE のポイント
  • 公式ドキュメントには「本番環境では、ほかに方法がない場合を除き、基本ロールを付与しない」とある
  • ロールを選ぶ順番は、事前定義ロール → 合うものがなければカスタムロール
  • カスタムロールは、組織またはプロジェクトで作る。「フォルダでカスタムロールを作る」選択肢は誤り
  • オーナー（管理者）は、IAM ポリシーの変更も含めてほぼすべてを操作できる。編集者（書き込み）は、ほとんどのリソースを変更できるが、IAM ポリシーは変更できない
  • 問題文や選択肢には、従来の名前（オーナー・編集者・閲覧者）と新しい名前（管理者・書き込み・読み取り）のどちらが出ても読めるようにしておく

4. 許可ポリシーの中身

許可ポリシーは YAML または JSON のオブジェクトで、ロール バインディングのリストが入っています。#1 のハンズオンで gcloud projects get-iam-policy を実行したときに表示されたのが、プロジェクトに付いている許可ポリシーです。

bindings:
- role: roles/run.invoker            # 何を
  members:                           # 誰に（複数書ける）
  - group:dev@example.com
  - serviceAccount:app@PROJECT_ID.iam.gserviceaccount.com
- role: roles/storage.objectViewer
  members:
  - user:alex@example.com
  condition:                         # 条件（任意）
    title: expires-end-of-2026
    expression: request.time < timestamp("2027-01-01T00:00:00Z")
etag: BwXXXXXXXXXX=                  # 同時に更新したときの競合を防ぐための値
version: 3
  • ロール バインディング：1つのロールと、それを与えるプリンシパルのリスト
  • 条件（IAM Conditions）：「期限まで」「特定の名前のリソースだけ」などの条件を付けられる。従来の基本ロール（オーナー・編集者・閲覧者）には条件を付けられない
  • etag：ほかの人が同時にポリシーを書き換えたときに、上書き事故を防ぐための値

5. 拒否ポリシー：許可より先に判定される

許可ポリシーは足し算です。上の階層で付与された権限は、下の階層の許可ポリシーでは取り消せません（#1）。そこで、「誰がどんなロールを持っていても、この操作だけはさせない」というガードレールを作るのが拒否ポリシー（deny policies）です。

許可ポリシー拒否ポリシー
役割権限を与える権限を使えなくする
付けられる場所組織・フォルダ・プロジェクトのほか、バケットなど多くのサービスのリソース組織・フォルダ・プロジェクトだけ
1つのリソースに1つだけ最大 500 個（拒否ルールは合計 500 個まで）
中身ロール バインディング（ロール＋プリンシパル）拒否ルール（プリンシパル＋権限。ロールではなく権限を直接書く）
権限の書き方iam.roles.createiam.googleapis.com/roles.create
プリンシパルの書き方user:alex@example.com
group:admins@example.com		principal://goog/subject/alex@example.com
principalSet://goog/group/admins@example.com
継承上の階層から引き継がれる上の階層から引き継がれる
作成・変更に必要なロールオーナー、セキュリティ管理者など拒否管理者（roles/iam.denyAdmin）。組織で付与する。オーナーでも作れない

拒否ポリシーは JSON で書きます。次の例は、「プロジェクトの削除は、project-admins グループ以外の全員に禁止する」というものです。

{
  "displayName": "Only project admins can delete projects",
  "rules": [
    {
      "denyRule": {
        "deniedPrincipals": ["principalSet://goog/public:all"],
        "exceptionPrincipals": ["principalSet://goog/group/project-admins@example.com"],
        "deniedPermissions": ["cloudresourcemanager.googleapis.com/projects.delete"]
      }
    }
  ]
}
deniedPrincipals拒否する相手。principalSet://goog/public:all は全員
exceptionPrincipals例外にする相手。ここでは project-admins グループ
deniedPermissions拒否する権限。ここではプロジェクトの削除
  • 拒否ルールは、拒否するプリンシパル、例外にするプリンシパル、拒否する権限、例外にする権限、拒否の条件（任意）でできている。拒否の条件で使えるのは、リソースのタグに関する条件だけ
  • すべての権限を拒否できるわけではない。対象になる権限は公式ドキュメントの一覧で確認する
  • 作成は gcloud iam policies create POLICY_ID --attachment-point=… --kind=denypolicies --policy-file=…。付け先（attachment point）は、プロジェクトなら cloudresourcemanager.googleapis.com/projects/PROJECT_ID の形で指定する
ACE のポイント
  • 「上の階層で付与されたロールのうち、一部の権限だけを特定のプロジェクトで使わせたくない」→ 下の階層の許可ポリシーでは取り消せないので、拒否ポリシーを使う（または付与する階層を見直す）
  • 拒否は許可より優先される。拒否ルールに該当すれば、オーナーなどの強いロールを持っていても使えない
  • 「誰に」を決めるのが IAM（許可・拒否）、「どんな設定を許すか」を決めるのが組織ポリシー（#1）。拒否ポリシーと組織ポリシーを混同しない
テックリードの視点：「ロールはあるのに Permission denied」 拒否ポリシーは組織の管理者がガードレールとして設定するもので、プロジェクトの許可ポリシーを見ても表示されません。ロールを持っているはずなのに拒否される場合は、組織ポリシーとあわせて、上の階層の拒否ポリシーも疑います。拒否ポリシーの一覧は gcloud iam policies list --attachment-point=… --kind=denypolicies で確認できます（見るにはオーナーなどの閲覧権限が必要）。

IAM には、このほかに Principal Access Boundary ポリシーなどの種類もあります。まずは許可ポリシーと拒否ポリシーを押さえれば十分です。

6. サービスアカウント：アプリの身元

サービスアカウントは、人ではなく、アプリケーションやワークロードが使うアカウントです。Cloud Run や VM で動くアプリが、バケットを読んだり別の API を呼んだりするときに、この身元で権限が判定されます。

6-1. サービスのリソースは「誰に」になれない

許可ポリシーの「誰に」に書けるのは、項番2の表のような身元（ID）だけです。Cloud Run サービスや VM そのものを書く種類はありません。そこで、コードを動かすサービスのリソースにはサービスアカウントを関連付けます（attach。公式ドキュメントでは「接続されたサービス アカウント」と訳されている箇所もあります）。中で動くアプリは、関連付けられたサービスアカウントの短期の認証情報を自動で受け取ります。ほかのリソースにアクセスすると、Google Cloud からは「そのサービスアカウントからのリクエスト」に見えます。

このため、同じ Cloud Run サービスでも、入ってくる通信と出ていく通信では、判定に使う許可ポリシーが違います。

判定することどこで誰に何を
① alice が A を呼び出せるかCloud Run サービス Aaliceroles/run.invoker
② A のアプリが B を読めるかバケット Bapp-saroles/storage.objectViewer

コマンドでも、許可ポリシーを付ける先（どこで）が違います。

# ① A の許可ポリシーに付ける
gcloud run services add-iam-policy-binding A \
  --region=REGION --member=user:alice@example.com --role=roles/run.invoker

# ② B の許可ポリシーに付ける
gcloud storage buckets add-iam-policy-binding gs://B \
  --member=serviceAccount:app-sa@PROJECT_ID.iam.gserviceaccount.com \
  --role=roles/storage.objectViewer
  • サービスアカウントを関連付けることができるのは、VM や Cloud Run のように自分でコードを動かすリソース。バケット、Pub/Sub トピック、Secret Manager のシークレットなどには関連付けない
  • リソースと身元が分かれているので、複数のサービスで同じサービスアカウントを使うことも、サービスごとに分けて権限を最小にすることもできる。監査ログには「どのサービスアカウントが操作したか」が残る
  • 何も指定しないと、Cloud Run や VM には Compute Engine のデフォルトのサービスアカウントが使われる（6-3）

6-2. サービスアカウントの2つの顔

サービスアカウントはプリンシパル（権限を受け取る側）であり、同時にリソース（ほかのプリンシパルに、それを使う権限を与える対象）でもあります。ACE でよく問われるポイントです。

「どこで」がサービスアカウントのときに付与するロールは、そのサービスアカウントを使うものと、そのサービスアカウントを管理するものに分かれます。

種類ロールできること
使うサービス アカウント ユーザー
roles/iam.serviceAccountUser		そのサービスアカウントを、Cloud Run や VM などのリソースに関連付けることができる
サービス アカウント トークン作成者
roles/iam.serviceAccountTokenCreator		そのサービスアカウントの短期の認証情報を発行して、そのサービスアカウントとして操作できる（サービス アカウントの権限借用、impersonation）
Workload Identity User
roles/iam.workloadIdentityUser		GKE や Workload Identity 連携のワークロードから、そのサービスアカウントの権限を借用できる
Service Account OpenID Connect Identity Token Creator
roles/iam.serviceAccountOpenIdTokenCreator		そのサービスアカウントの OIDC ID トークンだけを発行できる
管理するService Account Admin
roles/iam.serviceAccountAdmin		サービスアカウントの設定の変更や削除、このサービスアカウントの許可ポリシーの変更

roles/iam.serviceAccountKeyAdmin		サービスアカウント キーの作成や削除（6-4）

どれも、サービスアカウントのほか、プロジェクトなどの上の階層でも付与できます。プロジェクトで付与すると、そのプロジェクトのすべてのサービスアカウントが対象になるので、必要なサービスアカウントにだけ付与するのが安全です。ACE でよく問われるのは、ユーザー（関連付け）とトークン作成者（権限借用）の違いです。

権限借用は、許可された人が一時的にサービスアカウントの権限を借りる正規の仕組みです。借りられる認証情報の有効期間は数時間程度で、ほとんどの監査ログには、借りた人とサービスアカウントの両方が記録されます。AWS の AssumeRole に近いものです。

サービスアカウントの許可ポリシーでは、そのサービスアカウントが「何をできるか」は決まらない 「どこで」をサービスアカウントにした許可ポリシーで決まるのは、誰がそのサービスアカウントを使えるか・管理できるかです。app-sa にバケットを読ませたいなら、ロールはバケット側の許可ポリシーで、app-sa を「誰に」にして付与します（図4の②）。 
app-sa の許可ポリシー     … 誰が app-sa を使える？   （例：alice に serviceAccountUser）
バケット B の許可ポリシー … 誰が B を読める？        （例：app-sa に storage.objectViewer）
ロールの名前は「〜する人」、権限の名前は「サービス.リソース.動詞」 roles/iam.serviceAccountUser には動詞がありません。事前定義ロールの ID は roles/サービス.ロール名 の形で、ロール名は「どんな人向けか」を表す名詞になっているからです（objectViewer＝オブジェクトを見る人、run.invoker＝呼び出す人、serviceAccountUser＝サービスアカウントを使う人）。動詞は、ロールの中の権限のほうに入っています。 
$ gcloud iam roles describe roles/iam.serviceAccountUser
includedPermissions:
- iam.serviceAccounts.actAs     ← サービスアカウントとして振る舞う（これが関連付けに必要な権限）
- iam.serviceAccounts.get
- iam.serviceAccounts.list
- resourcemanager.projects.get
- resourcemanager.projects.list

6-4. サービスアカウント キーは最後の手段

サービスアカウント キーは、サービスアカウントとして認証するための秘密鍵ファイル（JSON）です。流出すると、持っている人が誰でもそのサービスアカウントになれてしまうため、公式ドキュメントでも「可能な限り、より安全な代替手段を選ぶ」よう勧めています。

やりたいことキーを使わない方法
GCP 上のアプリ（Cloud Run、VM など）に権限を与えたいサービスアカウントをリソースに関連付ける
GCP の外（GitHub Actions、AWS、オンプレミスなど）から GCP を操作したいWorkload Identity 連携で、外部の ID を使って認証する
開発者が、手元でサービスアカウントの権限を試したいサービスアカウントの権限借用（トークン作成者ロール）

2024年5月3日以降に作られた組織では、サービスアカウント キーの作成も、組織ポリシーで最初から禁止されています（constraints/iam.managed.disableServiceAccountKeyCreation）。

GCPAWS で近いもの注意点

8. 最小権限で設計する

  • 必要な権限だけを与える。まずは事前定義ロールから、用途に合う最も狭いものを選ぶ
  • 個人ではなくグループに付与する。人の出入りはグループで管理する
  • 必要な階層だけに付与する。上の階層で与えた権限は、下の階層の許可ポリシーでは取り消せない（#1）。どうしても止めたい操作は拒否ポリシーで防ぐ
  • アプリごとに専用のサービスアカウントを作る。デフォルトのサービスアカウントをそのまま使わない
  • サービスアカウント キーは作らない。関連付け、Workload Identity 連携、権限借用で代替する
テックリードの視点：チームの権限設計の例
グループ開発用プロジェクト本番用プロジェクト
開発チーム担当サービスの事前定義ロール（デプロイや確認に必要な分）閲覧系のロールのみ（ログの閲覧など）
リード・運用担当同上デプロイなど、必要な操作のロール
CI/CD専用のサービスアカウント。外部の CI から使うなら Workload Identity 連携で、キーは発行しない
オフショアのチームでも同じです。メンバーの入れ替わりがあっても、グループのメンバーを変えるだけで済むようにしておきましょう。

9. ハンズオン：サービスアカウントにロールを付与する

学習用のプロジェクトで、サービスアカウントを作り、ロールを付与して確認し、最後に片付けます。サービスアカウントの作成とロールの付与に費用はかかりません。学習用の configuration を有効にしたターミナルで実行し、PROJECT_ID は自分の学習用プロジェクトの ID に置き換えてください。

手順1. ロールの中身を見比べる（読み取りのみ）

# 事前定義ロール：Storage オブジェクト閲覧者
gcloud iam roles describe roles/storage.objectViewer

# 基本ロール：閲覧者（権限の数を数える）
gcloud iam roles describe roles/viewer --format="value(includedPermissions)" | tr ';' '\n' | wc -l

# オーナーが持つ、拒否ポリシーに関する権限
gcloud iam roles describe roles/owner --format="value(includedPermissions)" | tr ';' '\n' | grep denypolicies

# プロジェクトに付いている拒否ポリシーを一覧する
gcloud iam policies list \
  --attachment-point=cloudresourcemanager.googleapis.com/projects/PROJECT_ID \
  --kind=denypolicies

手順2. サービスアカウントを作る

# IAM の API を有効にする（すでに有効なら何も起きない）
gcloud services enable iam.googleapis.com

# サービスアカウントを作る
gcloud iam service-accounts create study-reader --display-name="Study reader"

# 一覧で確認する
gcloud iam service-accounts list

手順3. プロジェクトでロールを付与する

gcloud projects add-iam-policy-binding PROJECT_ID \
  --member="serviceAccount:study-reader@PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/storage.objectViewer" \
  --condition=None

--condition=None は「条件なしのバインディングを追加する」という指定です。付けないと、条件を入力するよう聞かれることがあります。

手順4. 付与されたことを確認する（読み取りのみ）

gcloud projects get-iam-policy PROJECT_ID \
  --flatten="bindings[].members" \
  --filter="bindings.members:serviceAccount:study-reader@" \
  --format="table(bindings.role,bindings.members)"

手順5. 片付ける（この順番で）

# ① 先にロールの付与を外す
gcloud projects remove-iam-policy-binding PROJECT_ID \
  --member="serviceAccount:study-reader@PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/storage.objectViewer" \
  --condition=None

# ② それからサービスアカウントを削除する
gcloud iam service-accounts delete study-reader@PROJECT_ID.iam.gserviceaccount.com

Q1. 手順1で、Storage オブジェクト閲覧者と閲覧者の権限の数はどれくらい違ったでしょう？そこから何が言えるでしょう？

答えを見る

Storage オブジェクト閲覧者は 8 個、閲覧者は約 6,350 個でした（2026-11 時点）。Storage オブジェクト閲覧者が「Cloud Storage のオブジェクトを読む」ことだけに絞られているのに対し、閲覧者は約300のサービスにまたがって、VM の一覧、Cloud Run や Cloud SQL の設定、シークレットの名前、ログなど、ほぼすべての設定や状態を見られるロールです。ログにはアプリが出力した内容も含まれるので、見せたくない情報まで見えてしまう可能性があります。なお、バケットの中のオブジェクト、シークレットの値、BigQuery のテーブルのデータなど、データそのものの中身は閲覧者には含まれません（2026-11 時点で確認）。「閲覧だけだから閲覧者で」と安易に選ばず、必要なサービスの事前定義ロールを選ぶ理由がここにあります。

Q2. 手順3で、ロールをプロジェクトで付与しました。このサービスアカウントは、どの範囲のバケットのオブジェクトを読めるでしょう？

答えを見る

プロジェクトのすべてのバケットのオブジェクトを読めます。プロジェクトで付与したロールは、その子にあたるすべてのリソースに引き継がれるからです（#1）。特定のバケットだけを読ませたいなら、そのバケットの許可ポリシーで付与します（gcloud storage buckets add-iam-policy-binding）。

Q3. 手順5で、先にロールの付与を外したのはなぜでしょう？

答えを見る

サービスアカウントを先に削除すると、許可ポリシーには deleted:serviceAccount:… という形でバインディングが残ってしまいます。ポリシーが散らかり、あとで「これは何だったか」が分からなくなります。付与を外してから削除するのが、きれいな片付け方です。

Q4. 手順1の後半の2つのコマンドの結果から、何が分かるでしょう？

答えを見る

オーナーが持つ拒否ポリシーの権限は iam.denypolicies.get と iam.denypolicies.list だけです（2026-11 時点）。つまりオーナーは拒否ポリシーを見ることはできても、作ることはできません。作るには拒否管理者（roles/iam.denyAdmin）が必要で、これは組織で付与するロールです。組織のない個人アカウントでは拒否ポリシーを試せないので、このハンズオンでは一覧の確認だけにしています（作成は検証していません）。

一覧のコマンドは {} を返します。このプロジェクトには拒否ポリシーが1つもない、という意味です。

10. 確認テスト（ACE 形式）

問1. Compute Engine の VM で動くアプリが、Cloud Storage のバケットからファイルを読む必要があります。最も安全な方法はどれでしょう？

  1. サービスアカウント キーを作成し、VM の中に保存してアプリから読み込む
  2. Compute Engine のデフォルトのサービスアカウントをそのまま使う
  3. アプリ専用のサービスアカウントを作り、Storage オブジェクト閲覧者を付与して、VM に関連付ける
  4. 開発者の Google アカウントの認証情報を VM に設定する
答えを見る

正解：C

アプリ専用のサービスアカウントに必要なロールだけを付与し、リソースに関連付けるのが基本です。A はキーが流出するリスクがあります。B は、編集者ロールが自動で付与されている場合、権限が広すぎます。D は個人の認証情報をアプリに使っていて、権限も責任の所在も不適切です。

問2. あなたのチームは、Cloud Run にアプリケーションをデプロイしています。アプリケーションは、ユーザー管理のサービスアカウント app-sa の身元で動かす必要があります。プロジェクトで Cloud Run 開発者（roles/run.developer）のロールを持つ開発者が、--service-account に app-sa を指定してデプロイしたところ、app-sa に対する iam.serviceAccounts.actAs の権限がないというエラーで失敗しました。最小権限の原則に従って、この問題を解決したいと考えています。どうすればよいですか。

  1. 開発者に、プロジェクトでサービス アカウント ユーザー（roles/iam.serviceAccountUser）のロールを付与する
  2. app-sa に、プロジェクトで Cloud Run 管理者（roles/run.admin）のロールを付与する
  3. 開発者に、app-sa でサービス アカウント ユーザー（roles/iam.serviceAccountUser）のロールを付与する
  4. 開発者に、app-sa でサービス アカウント トークン作成者（roles/iam.serviceAccountTokenCreator）のロールを付与する
答えを見る

正解：C

図5の②と同じ形です。誰に＝開発者、何を＝roles/iam.serviceAccountUser、どこで＝app-sa。サービスアカウントを関連付けるには、そのサービスアカウントの iam.serviceAccounts.actAs 権限が必要で、この権限はサービス アカウント ユーザーに含まれています。

この権限が必要なのは、関連付けたサービスは app-sa の権限で動くからです。誰でも関連付けることができると、開発者は自分が持っていない権限（app-sa が持つ権限）を、Cloud Run を通して使えてしまいます。

  • A：これでもエラーは解消します。ただし、プロジェクトで付与すると、プロジェクトのすべてのサービスアカウントを関連付けられるようになり、最小権限ではありません。「最小権限」と書かれていたら、付与する場所が狭いほうを選びます
  • B：ロールを受け取る相手が違います。足りないのは開発者の権限で、app-sa の権限ではありません
  • D：トークン作成者は、app-sa の短期の認証情報を発行する（権限を借用する）ためのロールです。iam.serviceAccounts.actAs は含まれていないので、関連付けはできません

問3. 組織内の複数のプロジェクトで、特定の3つの権限だけを持つロールを使いたい。合う事前定義ロールはありません。どうすればよいでしょう？

  1. 各プロジェクトの親フォルダで、カスタムロールを作成する
  2. 組織でカスタムロールを作成し、各プロジェクトで付与する
  3. 3つの権限を含む最も小さい基本ロールを付与する
  4. 3つの権限を、プリンシパルに直接付与する
答えを見る

正解：B

カスタムロールは組織またはプロジェクトで作れます。複数のプロジェクトで使うなら、組織で作れば1回で済みます。A のフォルダでは作れません。C の基本ロールは広すぎます。D の権限は、プリンシパルに直接付与できません（必ずロールを通す）。

問4. 協力会社のメンバー10人に、本番プロジェクトのログの閲覧だけを許可したい。今後メンバーの入れ替わりがあります。最も適切な方法はどれでしょう？

  1. 10人それぞれに、プロジェクトで閲覧者（roles/viewer）を付与する
  2. Google グループを作って10人を入れ、プロジェクトでグループにログ閲覧者（roles/logging.viewer）を付与する
  3. Google グループを作って10人を入れ、プロジェクトでグループに編集者を付与する
  4. プロジェクトで allAuthenticatedUsers にログ閲覧者を付与する
答えを見る

正解：B

グループに付与すれば、入れ替わりはグループのメンバーを変えるだけで済みます。ロールは目的に合う事前定義ロール（ログ閲覧者）を選びます。A は個人への付与で、閲覧者は範囲が広すぎます。C は変更までできてしまいます。D は Google アカウントを持つ世界中の誰でもログを見られる状態になります。

問5. GitHub Actions から、GCP の Cloud Run にデプロイしたい。最も安全な認証方法はどれでしょう？

  1. サービスアカウント キーを作り、GitHub のシークレットに保存する
  2. Workload Identity 連携を設定し、GitHub の ID トークンでサービスアカウントの権限を使う
  3. 開発者の Google アカウントでログインした認証情報を、GitHub のシークレットに保存する
  4. Cloud Run サービスに allUsers でデプロイ権限を付与する
答えを見る

正解：B

Workload Identity 連携なら、長期間有効な鍵を GitHub に置かずに済みます。A はキーが流出するリスクがあり、新しい組織ではキーの作成自体が組織ポリシーで禁止されています。C は個人の認証情報の流用です。D は誰でもデプロイできてしまいます。

問6. 開発チームのグループは、フォルダ「本番」でオーナーを持っています。運用の都合ですぐには外せません。それでも、本番のプロジェクトの削除だけは、管理者のグループ以外にはさせたくありません。どうすればよいでしょう？

  1. 本番の各プロジェクトの許可ポリシーで、開発チームのグループに閲覧者を付与する
  2. フォルダ「本番」に拒否ポリシーを付け、全員に対して cloudresourcemanager.googleapis.com/projects.delete を拒否し、管理者のグループを例外にする
  3. 組織ポリシーで、開発チームのグループがプロジェクトを削除できないようにする
  4. 本番の各プロジェクトの許可ポリシーから、開発チームのグループのオーナーを削除する
答えを見る

正解：B

拒否ポリシーは許可より先に判定されるので、オーナーを持っていても削除できなくなります。フォルダに付ければ、配下のプロジェクトすべてに引き継がれます。管理者だけは例外にするため、exceptionPrincipals に管理者のグループを書きます。

A は足し算なので、オーナーの権限は残ります。C の組織ポリシーは「どんな設定を許すか」を決めるもので、特定のグループを対象にはできません。D のオーナーはフォルダで付与されたもので、プロジェクトの許可ポリシーには書かれていません。

まとめ

  • IAM は「誰に（プリンシパル）・何を（ロール）・どこで（許可ポリシーを付けたリソース）」で考える
  • 権限は必ずロールにまとめて付与する。ロールは事前定義ロールから選び、合わなければカスタムロール（組織かプロジェクトで作る）。基本ロール（管理者・書き込み・読み取りと、従来のオーナー・編集者・閲覧者）は本番で原則使わない
  • 拒否ポリシーは許可より先に判定され、拒否されればどんなロールを持っていても使えない。組織・フォルダ・プロジェクトに付けられ、ロールではなく権限を直接書く。作るには組織で付与する拒否管理者が必要
  • チームへの付与はグループで行う。allUsers と allAuthenticatedUsers は社外も含む
  • Cloud Run や VM などのサービスのリソースは「誰に」になれないので、サービスアカウントを関連付ける。入ってくる通信はそのリソース自身の許可ポリシー、出ていく通信は関連付けられたサービスアカウントを「誰に」にして、行き先の許可ポリシーで判定される
  • サービスアカウントはアプリの身元で、プリンシパルでもありリソースでもある。サービスアカウントの許可ポリシーで決まるのは「誰が使えるか・管理できるか」。関連付けにはサービス アカウント ユーザー、権限借用にはトークン作成者が必要
  • サービスアカウント キーは最後の手段。関連付け、Workload Identity 連携、権限借用で代替する
