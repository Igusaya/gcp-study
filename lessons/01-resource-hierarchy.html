#1 リソース階層と課金

GCP のリソースがどう整理され、権限・ルール・お金がどう流れるかを理解する

この回のゴール
  • 組織・フォルダ・プロジェクト・サービスのリソースの4つの階層を説明できる
  • IAM の権限が上の階層から引き継がれる仕組みと、その注意点を説明できる
  • IAM と組織ポリシーの違い、課金と階層の関係を説明できる
  • 請求先アカウントが何で、プロジェクトの紐付けにどの権限が必要か説明できる
  • 新しく参画した環境で、何を確認すればよいか分かる

1. 4つの階層

階層役割AWS で近いもの
組織会社全体のルート。Google Workspace または Cloud Identity のドメインと 1 対 1 で対応するAWS Organizations のルート
フォルダプロジェクトをまとめる。入れ子にできる（最大10階層）OU（組織単位）
プロジェクトサービスのリソースを入れる箱。API の有効化、割り当て、課金の紐付けはプロジェクト単位AWS アカウント（ただし、作るのはずっと手軽）
サービスのリソースVM、Cloud Run のサービス、バケットなど。必ずどれか1つのプロジェクトに属する各リソース
用語（公式ドキュメントに準拠）
  • 公式ドキュメントでは、組織・フォルダ・プロジェクトもそれぞれ organization resource / folder resource / project resource と呼ばれ、すべて「リソース」です
  • 階層の一番下にある VM やバケットなどは、service resources（サービスのリソース）と呼ばれます
  • 組織・フォルダ・プロジェクトのように、ほかのリソースを中に含むリソースは container resource と呼ばれます
  • 階層上の位置関係は parent（親）・child（子）・ancestors（祖先）で表します。組織は階層の root node です

2. IAM の権限は上から引き継がれる

IAM の許可ポリシー（誰にどのロールを与えるか）は、上の階層で設定すると、下の階層すべてに引き継がれます。

ACE のポイント
  • 実際に効く権限は、操作するリソースと、その祖先（上の階層）すべての IAM 許可ポリシーの合計
  • 上の階層で与えた権限は、下の階層の許可ポリシーでは取り消せない
  • そのため、権限はできるだけ下の階層で、必要な分だけ与えるのが原則
  • 権限を「引き算」できるのは、別の仕組みである IAM 拒否ポリシー。拒否ポリシーは組織・フォルダ・プロジェクトに設定でき、許可ポリシーより優先される
  • 複数のプロジェクトに同じ権限を配りたいときは、フォルダにまとめてフォルダで付与すると管理が楽になる

3. 組織ポリシー：「どんな設定を許すか」

IAM は「誰が何をできるか」を決める仕組みです。これとは別に、組織ポリシーで「この組織ではどんな設定を許すか」を決められます。組織ポリシーも、上の階層から引き継がれます。

3-1. 組織・フォルダ・プロジェクトには、IAM と組織ポリシーの両方を設定できる

「組織ポリシー」は仕組みの名前で、「組織にしか設定できないポリシー」という意味ではありません。組織・フォルダ・プロジェクトのどれにも、IAM と組織ポリシーの両方を設定できます。

IAM 許可ポリシー組織ポリシー
決めること誰が何をできるかどんな設定を許すか
設定できる場所組織、フォルダ、プロジェクト、一部のサービスのリソース組織、フォルダ、プロジェクト
引き継ぎ方下に引き継がれ、合計で効く。下の階層の許可ポリシーでは取り消せない（引き算は拒否ポリシーで行う）下に引き継がれる。下の階層で上書きすることもできる
設定・上書きできる人そのリソースの IAM を管理できる人組織ポリシー管理者。このロールは組織の階層でしか付与できないため、実務では中央の管理者に限られる

IAM 拒否ポリシーも、組織・フォルダ・プロジェクトに設定できます。

3-2. 操作が成功するまでの判定

項番2の「合計」は、IAM の中で各階層のポリシーをどう組み合わせるかの話です。図3の「両方を満たす」は、IAM と組織ポリシーという別々の仕組みをどう組み合わせるかの話です。2つを合わせると、判定は次のようになります。

テックリードの視点：失敗の原因を見分ける 権限が足りないときは「権限（permission）がない」という内容のエラーになります。組織ポリシーに違反したときは、エラーメッセージに constraints/... が含まれます。どちらの仕組みで止められたのかを見分けると、相談先（IAM の管理者か、組織ポリシーの管理者か）がすぐに分かります。

よく使われる組織ポリシーの例：

やりたいこと制約（constraint）
リソースを作れるリージョンを限定するconstraints/gcp.resourceLocations
VM に外部IPアドレスを付けることを禁止するconstraints/compute.vmExternalIpAccess
新しいプロジェクトで default ネットワークを自動作成しないconstraints/compute.skipDefaultNetworkCreation
AWS との比較 組織全体の「ガードレール」という意味で、AWS の SCP に近い位置づけです。ただし SCP が「権限」を制限するのに対し、組織ポリシーは「リソースの設定」を制限します。特定の人の権限を制限したいなら、IAM 拒否ポリシーを使います。

4. 課金は階層とは別の線でつながる

GCP の料金は、請求先アカウント（Cloud Billing account）を通して支払います。名前に「アカウント」と付いていますが、ログインに使うアカウントとは別物です。ここではまず「請求先アカウントとは何か」を整理し、次に階層との関係、最後にプロジェクトを紐付けるのに必要な権限を見ます。

4-1. 請求先アカウントは「ログインするアカウント」ではない

課金の話には、「アカウント」と付くものや、それに近いものが3つ出てきます。混ざりやすいので、最初に区別しておきます。

名前何か例
Google アカウント
（ユーザー アカウント）		ログインする人。IAM のプリンシパルになるuser:alice@example.com
請求先アカウント
（Cloud Billing account）		GCP のリソースの一つ。紐付いたプロジェクトの費用を記録し、お支払いプロファイルを使って支払うXXXXXX-XXXXXX-XXXXXX 形式の ID
お支払いプロファイル
（Google payments profile）		誰がどうやって払うか。名前、住所、カードや銀行口座などを持つ。GCP だけでなく Google の各サービスで共通種類は「個人」と「組織」の2つ
  • Google アカウントと請求先アカウントは同じものではありません。Google アカウント（プリンシパル）が、請求先アカウント（リソース）の許可ポリシーでロールを持つ、という関係です。#2 IAM で扱う「誰に・何を・どこで」と同じ形です
  • 会社では、社員の Google アカウント（user:）や Google グループ（group:）に、請求先アカウントのロールを付与します。たとえば経理の担当者には管理者のロールを付与する、といった形です
  • 実際にお金を払う手段（カードなど）を持っているのは、お支払いプロファイルです。請求先アカウントは、どのプロジェクトの費用をどのお支払いプロファイルで払うかをまとめるものです
請求先アカウントは「サービスのリソース」ではない 公式ドキュメントでは、サービスのリソースは「プロジェクトの中にあるもの」（Compute Engine の VM や Cloud Storage のバケットなど）です。請求先アカウントはプロジェクトの中にはありません。公式ドキュメントでは階層の分類名は付けられておらず、そのまま「請求先アカウント（Cloud Billing account）」と呼ばれています。

4-2. 階層の中での位置

親（IAM の継承元）プロジェクトとの関係
サービスのリソースプロジェクトプロジェクトの中にある
請求先アカウント組織。組織がない個人アカウントでは親なし紐付けて費用を払うだけ。親子ではない
  • 請求先アカウントは1つの組織が所有します。組織で付与した課金のロールは、その組織が所有する請求先アカウントにも継承されます
  • 請求先アカウントは、IAM の意味ではプロジェクトの親ではありません。そのため、請求先アカウントで付与したロールはプロジェクトには継承されません
  • 紐付けは組織の所有とは関係がありません。ほかの組織のプロジェクトの費用を払うこともできます
  • 1つのプロジェクトが紐付けられる請求先アカウントは1つだけです
  • 1つの請求先アカウントには複数のプロジェクトを紐付けられます。ただし、紐付けられる数には上限（割り当て）があります
  • 請求先アカウントを紐付けていないプロジェクトでは、Compute Engine など課金が必要なサービスを使えません

4-3. 紐付けに必要な権限

プロジェクトを請求先アカウントに紐付ける操作は、2つのリソースにまたがります。そのため、紐付けを行う人は、両方のリソースの許可ポリシーでロールを持っている必要があります。

  • 請求先アカウントの許可ポリシー：roles/billing.user（Billing Account User）。「この請求先アカウントにプロジェクトを紐付けてよい」という権限
  • プロジェクトの許可ポリシー：roles/billing.projectManager（Project Billing Manager）。「このプロジェクトの紐付けを変えてよい」という権限。プロジェクトのオーナー（roles/owner）はこの権限を含む
  • ここでのプリンシパル（alice）は操作する人で、お金を払う人ではありません。払うのは請求先アカウントにつながったお支払いプロファイルです

課金の主な事前定義ロールは次のとおりです。

ロールできること付与できる場所
roles/billing.creator
Billing Account Creator		新しい請求先アカウント（セルフサービス）を作る組織だけ
roles/billing.admin
Billing Account Administrator		請求先アカウントを管理する（作成はできない）。プロジェクトの紐付けと解除もできる組織、請求先アカウント
roles/billing.user
Billing Account User		プロジェクトを請求先アカウントに紐付ける組織、請求先アカウント
roles/billing.costsManager
Billing Account Costs Manager		予算を管理し、費用の情報を見たりエクスポートしたりする組織、請求先アカウント
roles/billing.viewer
Billing Account Viewer		費用や支払いの情報を見る組織、請求先アカウント
roles/billing.projectManager
Project Billing Manager		プロジェクトの紐付けと解除組織、フォルダ、プロジェクト
ACE のポイント
  • 「プロジェクトを請求先アカウントに紐付けられない」という問題では、請求先アカウントの roles/billing.user と、プロジェクトの roles/billing.projectManager（またはオーナー）の両方がそろっているかを確認する
  • roles/billing.admin でも請求先アカウントは作れない。作るには組織の roles/billing.creator が必要
  • 請求先アカウントはプロジェクトの親ではないので、請求先アカウントで付与したロールはプロジェクトに継承されない
予算アラートは「通知」だけ 予算アラートはしきい値を超えると通知を送りますが、課金を止めるわけではありません。しきい値には、実際の支出（CURRENT_SPEND）と、月末までの予測額（FORECASTED_SPEND）のどちらも使えます。予測額を使うと、超えそうになった時点で事前に気づけます。

5. 個人アカウントと業務環境の違い

個人アカウント業務環境（一般的なケース）
組織なしあり
プロジェクトの親なし組織またはフォルダ
自分の権限自分がオーナー管理者に付与された分だけ
組織ポリシー使えない組織全体のルールがかかっていることが多い
テックリードの視点：参画初日に確認したいこと
  • 組織とフォルダの構成。環境（本番・ステージング・開発）ごとにプロジェクトが分かれているか
  • オーナーや編集者のロールを誰が持っているか。開発メンバーにどの階層で、どのロールが付いているか
  • 適用されている組織ポリシー
  • どの請求先アカウントで費用を払っているか。その請求先アカウントの管理者は誰か
  • 予算アラートが設定されているか。誰に通知が届くか
  • 本番のプロジェクトを操作するときのルール（誰が、どんな手順で操作するか）

6. ハンズオン：自分の環境を読み取る

学習用のターミナル（学習用の configuration を有効にしたもの）で実行します。どれも読み取りだけで、何も変更しません。PROJECT_ID は自分の学習用プロジェクトの ID に置き換えてください。

# ① 自分がアクセスできる組織を一覧する
gcloud organizations list

# ② プロジェクトの「先祖」（上の階層）を表示する
gcloud projects get-ancestors PROJECT_ID

# ③ プロジェクトの IAM 許可ポリシーを表示する
gcloud projects get-iam-policy PROJECT_ID

# ④ 自分がアクセスできる請求先アカウントを一覧する
gcloud billing accounts list

# ⑤ 請求先アカウントの親と、許可ポリシーを表示する
gcloud billing accounts describe BILLING_ACCOUNT_ID
gcloud billing accounts get-iam-policy BILLING_ACCOUNT_ID

BILLING_ACCOUNT_ID は、④で表示される ACCOUNT_ID に置き換えてください。

Q1. ①と②の結果から、このプロジェクトの階層はどうなっていると言えるでしょう？

答えを見る

①は Listed 0 items. で、アクセスできる組織がありません。②にはプロジェクト自身の1行しか出ません。つまり、組織もフォルダもなく、プロジェクトが最上位です（図9の左側）。Gmail の個人アカウントには組織リソースがないためで、これは正常です。

Q2. ③の結果で、誰がどのロールを持っているでしょう？

答えを見る

プロジェクトを作った自分のアカウントが roles/owner（オーナー）を持っています。オーナーは、プロジェクトのすべてを操作でき、IAM も変更できる最も強いロールです。

オーナー、編集者、閲覧者は「従来の基本ロール」と呼ばれます（新しい基本ロールとして、管理者・書き込み・読み取りもあります）。どれも範囲がとても広いので、本番環境ではなるべく使いません。詳しくは #2 IAM で扱います。

Q3. 参画先のプロジェクトで②を実行したら、どんな結果になりそうでしょう？

答えを見る

プロジェクトの上に、フォルダ（1つ以上）と組織が並ぶはずです。たとえば次のような形です。

ID              TYPE
myapp-prod      project
123456789012    folder
987654321098    organization

業務環境では、gcloud projects get-ancestors-iam-policy PROJECT_ID を使うと、上の階層すべての IAM ポリシーをまとめて確認できます。「この権限はどこから引き継がれているのか」を調べるときに便利です。

7. 確認テスト（ACE 形式）

問1. 開発チーム（Google グループ）に、開発用の3つのプロジェクトすべてで Compute Engine を管理させたい。開発用のプロジェクトは今後も増える予定です。最も運用の手間が少ない方法はどれでしょう？

  1. 各プロジェクトで、チームのメンバー一人ひとりに roles/compute.admin を付与する
  2. 3つのプロジェクトを「開発」フォルダにまとめ、フォルダでグループに roles/compute.admin を付与する
  3. 組織でグループに roles/owner を付与する
  4. 各プロジェクトで、グループに roles/editor を付与する
答えを見る

正解：B

フォルダで付与すると、配下のプロジェクトすべてに引き継がれます。新しいプロジェクトもフォルダに入れるだけで権限が付きます。また、個人ではなくグループに付与すれば、メンバーの増減はグループ側で管理できます。

A は、プロジェクトやメンバーが増えるたびに作業が必要です。C は権限が広すぎます（本番も含めた全体のオーナーになってしまう）。D は、プロジェクトごとの作業が必要なうえ、基本ロールで権限が広すぎます。

問2. ユーザー A は、フォルダ「開発」で roles/editor を持っています。配下のプロジェクト myapp-stg だけは、A に変更させたくありません。適切な方法はどれでしょう？

  1. myapp-stg の許可ポリシーで、A に roles/viewer を付与する
  2. myapp-stg に IAM 拒否ポリシーを設定し、A に対して該当する権限を拒否する
  3. 組織ポリシーで、A が myapp-stg を変更できないようにする
  4. myapp-stg の許可ポリシーから、A の roles/editor を削除する
答えを見る

正解：B

許可ポリシーは足し算なので、A に閲覧者を付与しても（A）、フォルダから引き継いだ編集者の権限は残ります。D の roles/editor はフォルダで付与されたものなので、myapp-stg のポリシーにはそもそも書かれていません。C の組織ポリシーは「どんな設定を許すか」を決めるもので、特定の人を対象にはできません。

拒否ポリシーのほかに、「A への付与をフォルダではなく、必要なプロジェクトごとに行う」ように見直すのも有効です。

問3. 会社のすべてのプロジェクトで、東京と大阪以外のリージョンにリソースを作れないようにしたい。どうすればよいでしょう？

  1. 各プロジェクトの IAM で、ほかのリージョンへのアクセスを拒否する
  2. 組織で、組織ポリシーの制約 constraints/gcp.resourceLocations を設定する
  3. 全員に、gcloud の compute/region を asia-northeast1 に設定するよう周知する
  4. 予算アラートで、ほかのリージョンでの支出を検知する
答えを見る

正解：B

「どんな設定を許すか」は組織ポリシーの役割です。組織で設定すれば、配下のすべてのプロジェクトに引き継がれます。

C の compute/region は、手元の gcloud でリージョンを省略したときの既定値にすぎず、強制力はありません（#0 で設定したものです）。D は事後に気づくだけで、作成を防げません。

問4. 新しく作ったプロジェクトで Compute Engine API を有効にしようとしたところ、失敗しました。最も可能性が高い原因はどれでしょう？

  1. プロジェクトに請求先アカウントが紐付いていない
  2. プロジェクトが組織に属していない
  3. gcloud にリージョンを設定していない
  4. プロジェクト名が、ほかのプロジェクトと重複している
答えを見る

正解：A

Compute Engine は課金が必要なサービスなので、請求先アカウントを紐付けないと有効にできません。B の組織がなくてもプロジェクトは使えます（個人アカウントがその例です）。D のプロジェクト名（表示名）は重複してもかまいません。一意である必要があるのはプロジェクト ID です。

問5. 開発者 X は、新しく作ったプロジェクト myapp-sandbox のオーナーです。このプロジェクトを会社の請求先アカウントに紐付けようとしたところ、権限が足りずに失敗しました。最小限の権限で紐付けられるようにするには、どうすればよいでしょう？

  1. 請求先アカウントの許可ポリシーで、X に roles/billing.user を付与する
  2. myapp-sandbox の許可ポリシーで、X に roles/billing.projectManager を付与する
  3. 組織の許可ポリシーで、X に roles/billing.admin を付与する
  4. 請求先アカウントの許可ポリシーで、X に roles/billing.viewer を付与する
答えを見る

正解：A

紐付けには、請求先アカウントとプロジェクトの両方の許可が必要です（図8）。X はプロジェクトのオーナーなので、プロジェクト側の権限（roles/billing.projectManager が含む権限）はすでに持っています。足りないのは請求先アカウント側の roles/billing.user です。

B は、X がすでに持っている権限なので効果がありません。C は、組織が所有するすべての請求先アカウントの管理者になってしまい、権限が広すぎます。D は閲覧だけなので紐付けられません。

問6. 組織ポリシーについて、正しいものはどれでしょう？

  1. 名前のとおり、組織にしか設定できない
  2. 組織だけでなく、フォルダやプロジェクトにも設定できる
  3. 特定のユーザーやグループを対象に、操作を制限できる
  4. Cloud Storage のバケットなど、個々のサービスのリソースに直接設定できる
答えを見る

正解：B

「組織ポリシー」は仕組みの名前で、組織・フォルダ・プロジェクトのどれにも設定できます（図4）。C のように「誰に対して」を決めるのは IAM の役割です。D のサービスのリソースには組織ポリシーを直接設定できませんが、上の階層から引き継いだ制約は適用されます。

まとめ

  • 階層は「組織 → フォルダ → プロジェクト → サービスのリソース」。サービスのリソースは必ず1つのプロジェクトに属する
  • IAM の許可ポリシーは上から引き継がれ、合計で効く（足し算）。下の階層の許可ポリシーでは取り消せない。引き算は拒否ポリシーで行い、拒否は許可より優先される
  • IAM は「誰が」、組織ポリシーは「どんな設定を」を決める。組織・フォルダ・プロジェクトのどれにも両方を設定でき、どちらも上から引き継がれる
  • 操作が成功するのは、IAM と組織ポリシーの両方の条件を満たしたときだけ
  • 請求先アカウントはログインするアカウントではなく、リソースの一つ。組織が所有でき、組織の課金のロールが継承される。プロジェクトとは紐付け（支払いの関係）でつながるだけで、IAM の親子ではない
  • 紐付けには、請求先アカウントの許可ポリシーで roles/billing.user、プロジェクトの許可ポリシーで roles/billing.projectManager（またはオーナー）が必要。予算アラートは通知だけ
