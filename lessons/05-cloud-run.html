#5 Cloud Run ハンズオン

コンテナ イメージを作って Artifact Registry に置き、Cloud Run にデプロイする。リビジョンとトラフィック、呼び出しの認証、サービス ID まで

この回のゴール
  • ソースコードが、コンテナ イメージ → Artifact Registry → Cloud Run サービスと進んで URL になるまでの流れを説明できる
  • Cloud Run のサービス・リビジョン・インスタンスの関係と、台数の増減のしかたを説明できる
  • 新しいリビジョンにトラフィックを流さずにデプロイし、一部だけ切り替えたり、元に戻したりできる
  • サービスを呼べる人（roles/run.invoker）と、サービスが使う権限（サービス ID）の違いを説明できる

1. 全体像：ソースコードから URL まで

Cloud Run は、コンテナ イメージを受け取って動かします。手元のソースコードからイメージを作り（ビルド）、Google Cloud のイメージ置き場である Artifact Registry に置き（push）、Cloud Run にそのイメージを指定してデプロイすると、URL が発行されます。

手順することコマンドの例
① ビルドDockerfile からコンテナ イメージを作るdocker build
② pushイメージを Artifact Registry のリポジトリに置くdocker push
③ デプロイイメージを指定して Cloud Run のサービスを作る・更新するgcloud run deploy --image

2. Artifact Registry：イメージの置き場所

Artifact Registry は、コンテナ イメージや言語のパッケージ（npm、Maven、Python など）を保管するサービスです。イメージはリポジトリに入れます。リポジトリは作るときに、形式（Docker など）とロケーション（リージョンなど）を決めます。

イメージの名前の読み方

asia-northeast1-docker.pkg.dev/PROJECT_ID/study-repo/hello:v1
部分意味
asia-northeast1-docker.pkg.devリポジトリのロケーション（東京）の、Docker 用のホスト
PROJECT_IDリポジトリがあるプロジェクト
study-repoリポジトリの名前
helloイメージの名前
v1タグ（バージョンなどの目印）。付け替えられる
  • 認証：docker push の前に gcloud auth configure-docker asia-northeast1-docker.pkg.dev を1回実行します。Docker の設定ファイル（~/.docker/config.json）の credHelpers に、このホストの認証を gcloud に任せる設定（gcloud CLI 認証情報ヘルパー）が追加されます。ほかのホストの設定はそのまま残ります
  • Container Registry（gcr.io）は以前のイメージ置き場です。非推奨になり、2025 年 3 月 18 日にシャットダウンされて、イメージを書き込めなくなりました。推奨されている後継が Artifact Registry です
  • ロケーションは、Cloud Run と同じリージョンにするのが基本です。同じロケーションの中のデータ転送は無料で、リージョンをまたぐと転送の料金がかかります
Apple シリコンの Mac でビルドするときの注意

Cloud Run のコンテナの実行ファイルは、Linux 64 ビット（x86_64）用にコンパイルされている必要があります（コンテナ ランタイムの契約）。Apple シリコン（M1 など）の Mac でそのまま docker build すると、linux/arm64 用のイメージができて、Cloud Run では期待どおりに動かないことがあります。公式ドキュメントでは、Cloud Build でビルドする方法が案内されています。

このハンズオンでは手元でビルドするので、docker build --platform linux/amd64 と指定して linux/amd64 用のイメージを作ります（--platform は Docker の機能で、Google Cloud のドキュメントには書かれていません）。

3. Cloud Run の仕組み

3-1. サービス・リビジョン・インスタンス

用語意味
サービスデプロイの単位。URL を持つ。リージョンのリソースで、名前とリージョンで区別する
リビジョンデプロイのたびに作られる、イメージと設定の組。作った後は変更できない。古いリビジョンも残るので、戻すことができる
インスタンスリビジョンのコンテナを実際に動かしているもの。リクエストの量に応じて自動で増減する

3-2. 台数の増減と料金

  • インスタンスあたりの最大同時リクエスト数：1つのインスタンスは、複数のリクエストを同時に処理します。上限を超えると、インスタンスが増えます。既定値は、gcloud で新しく作ったサービスでは vCPU の数 × 80（vCPU が 1 なら 80）、コンソールで作ったサービスでは 80 です。最大 1,000 まで増やせます
  • 最大インスタンス数：増えすぎを防ぐ上限です（既定ではリビジョンごとに 100）。データベースの接続数を守るときや、料金を抑えるときに使います
  • 最小インスタンス数：既定は 0 で、リクエストがないと 0 台まで減ります。0 台から最初のリクエストを受けると、インスタンスの起動を待つ（コールド スタート）ので応答が遅くなります。1 以上にすると速くなりますが、その台数分の料金がかかり続けます
  • 課金設定：既定のリクエスト ベースの課金では、リクエストを処理している間だけ CPU とメモリの料金がかかります（リクエストの数にも料金がかかる）。リクエストの処理が終わった後もバックグラウンドで処理を続けたいなら、インスタンス ベースの課金にします。以前はそれぞれ「リクエストの処理中にのみ CPU を割り当てる」「CPU を常に割り当てる」と呼ばれていたので、古い問題文ではこの名前で出ることがあります

3-3. リビジョンとトラフィック

新しいイメージや設定でデプロイすると、新しいリビジョンが作られ、既定ではすぐにすべてのトラフィックが新しいリビジョンに移ります。本番では、次のように段階的に切り替えることができます。

  1. --no-traffic と --tag を付けてデプロイする：新しいリビジョンにはトラフィックを流さず、タグ専用の URL（https://TAG---…run.app）でだけ呼べるようにする
  2. タグの URL で動作を確認する
  3. gcloud run services update-traffic で、少しずつ割合を増やす（例：10% → 50% → 100%）
  4. 問題が出たら、前のリビジョンに 100% を戻す（ロールバック）。古いリビジョンは残っているので、ビルドし直す必要はない

注意：トラフィックを分割したり、前のリビジョンに固定したりすると、その後のデプロイでもその割り当てが続き、新しいリビジョンには自動でトラフィックが移りません。最新のリビジョンに自動で移る状態に戻すには、update-traffic --to-latest を実行します。

4. 誰が呼べるか、サービスは何ができるか

#2 の 6-1 で学んだように、サービスのリソースでは「入ってくる通信」と「出ていく通信」を分けて考えます。Cloud Run では、入ってくる通信は サービスの許可ポリシーで、出ていく通信は サービス ID（サービスに関連付けたサービス アカウント）の権限で決まります。

4-1. 呼び出しの認証：誰が呼べるか

  • サービスを呼ぶには、サービス（またはプロジェクト）の許可ポリシーで、Cloud Run 起動元（roles/run.invoker）を持っている必要があります。持っていないと 403 が返ります
  • 呼ぶ側は、リクエストに ID トークンを付けます。開発者が試すときは、gcloud auth print-identity-token で取得したトークンを付けて curl で呼ぶか、gcloud run services proxy（Cloud Run プロキシ）を使います
  • 限定公開サービス（社内の API、ほかのサービスからだけ呼ばれるもの）にするときは --no-allow-unauthenticated でデプロイし、呼ぶ側のプリンシパル（ほかのサービスのサービス ID など）にだけ roles/run.invoker を付与します
  • 公開サービス（誰でも呼べる Web サイトや公開 API）にする方法は2つあります
    • Cloud Run 起動元の IAM チェックを無効にする（--no-invoker-iam-check）。公式ドキュメントではこちらが推奨です
    • allUsers に roles/run.invoker を付与する（--allow-unauthenticated）。組織ポリシーの「ドメインで制限された共有」で allUsers への付与が禁止されているとできません
  • --allow-unauthenticated と --no-allow-unauthenticated のどちらも付けずにデプロイすると、どちらにするかを聞かれます
  • ネットワーク上り（内向き）の設定（ingress）で、どこからのリクエストを受け付けるかも絞れます。この設定は IAM より先に評価されます
    • すべて（all）：インターネットから run.app の URL に直接届くリクエストも受け付ける（既定）
    • 内部（internal）：同じプロジェクトの VPC ネットワークや、同じプロジェクトの Cloud Scheduler・Pub/Sub などからだけ受け付ける
    • 内部と Cloud Load Balancing（internal-and-cloud-load-balancing）：内部に加えて、外部アプリケーション ロードバランサ経由も受け付ける

4-2. サービス ID：サービスは何ができるか

  • サービスの中のコードが Google Cloud の API を呼ぶときは、サービス ID の権限で呼びます
  • 指定しないと、Compute Engine のデフォルト サービス アカウントを使います。#4 の 2-1 で見たように、このサービス アカウントには編集者ロールが付いていることがあり、権限が大きすぎます
  • 推奨はユーザー管理のサービス アカウントです。サービスごとに専用のサービス アカウントを作り、必要なロールだけを付けて、--service-account で関連付けます
  • デプロイする人（デプロイ担当者アカウント）は、そのサービス アカウントに対するサービス アカウント ユーザーのロール（roles/iam.serviceAccountUser。iam.serviceAccounts.actAs を含む）を持っている必要があります（#2 の 6-2）

Cloud Run の主なロール

ロールできること
Cloud Run 管理者
roles/run.admin		Cloud Run のすべてのリソースを完全に管理できる。許可ポリシーの変更も含む
Cloud Run デベロッパー
roles/run.developer		Cloud Run のすべてのリソースの読み取りと書き込み（作成・更新・削除）。許可ポリシーは変更できない
Cloud Run 起動元
roles/run.invoker		サービスを呼び出す、ジョブを実行する
Cloud Run 閲覧者
roles/run.viewer		Cloud Run のすべてのリソースの状態を見る（許可ポリシーを含む）
ACE のポイント
  • 「新しいバージョンを一部のユーザーだけで試す」「カナリア リリース」→ --no-traffic（＋--tag）でデプロイし、update-traffic で割合を指定する。「すぐに元に戻したい」→ 前のリビジョンに 100% を戻す
  • 「誰でもアクセスできる」→ allUsers に roles/run.invoker（--allow-unauthenticated）、または Cloud Run 起動元の IAM チェックの無効化。「特定のサービスからだけ呼ばせたい」→ 呼ぶ側のサービス アカウントに roles/run.invoker。「インターネットから直接は届かないようにしたい」→ ネットワーク上り（内向き）の設定を内部に
  • 「Cloud Run から Cloud Storage などを使う。最小権限で」→ 専用のサービス アカウントを作り、必要なロールだけを付けて、サービス ID に指定する。デフォルト サービス アカウントやサービス アカウント キーは使わない
  • 「最初のリクエストが遅い（コールド スタート）」→ 最小インスタンス数を 1 以上にする（料金はかかり続ける）。「データベースの接続が多すぎる」「費用の上限」→ 最大インスタンス数
  • イメージは Artifact Registry に置く（Container Registry はシャットダウン済み）。gcloud run deploy --source なら、Cloud Build がビルドして Artifact Registry の cloud-run-source-deploy リポジトリに置く

5. テックリードの視点

参画したら確認したいこと
  • イメージのタグをどう付けているか（latest だけだと、どのリビジョンがどのコードか追えない。Git のコミット ID などを付けているか）
  • ビルドとデプロイを誰が・何で行っているか（手元の PC からか、Cloud Build や GitHub Actions などの CI/CD からか）
  • リリースは一気に切り替えているか、--no-traffic とタグで段階的に切り替えているか。ロールバックの手順は決まっているか
  • サービスごとに専用のサービス アカウントを使っているか。デフォルト サービス アカウントのままになっていないか
  • 公開サービス（allUsers に roles/run.invoker、または IAM チェックを無効化）はどれか。それは意図どおりか。ネットワーク上り（内向き）の設定はどうなっているか
  • 最小インスタンス数を 1 以上にしているサービスはどれか（使っていなくても料金がかかる）
  • オフショアチームへの説明：図1の①②③のどこで失敗しているかを切り分けると、問い合わせが速くなる。たとえば「push で 403」は Artifact Registry の権限や認証の設定、「デプロイ後に起動しない」はコンテナ（ポート、CPU のアーキテクチャ）の問題であることが多い
  • よくある誤解：「サービスを呼べる権限」と「サービスが使える権限」を混同しやすい。前者は roles/run.invoker（呼ぶ側に付ける）、後者はサービス ID（サービスに関連付けたサービス アカウント）のロール
  • 設計レビューの観点：アプリが状態を持っていないか（インスタンスはいつでも増減・停止するので、セッションやファイルはインスタンスの中に置かない）。設定値や秘密情報をイメージに含めていないか（環境変数や Secret Manager で渡す）

6. ハンズオン：イメージを作って Cloud Run にデプロイする

学習用の configuration を有効にしたターミナルで実行します（export CLOUDSDK_ACTIVE_CONFIG_NAME=study）。Docker が動いている必要があります。

料金について：このハンズオンの規模なら、無料枠に収まる見込みです。

  • Cloud Run（リクエスト ベースの課金）：毎月 180,000 vCPU 秒、360,000 GiB 秒、200 万リクエストまで無料。IAM で拒否されたリクエスト（手順7の 403）は課金されない
  • Artifact Registry：ストレージは毎月 0.5 GiB まで無料（今回のイメージは数十 MB）。同じリージョンの Cloud Run への転送は無料
  • 無料枠は、どちらも請求先アカウント単位で、プロジェクトをまたいで合算されます
  • イメージは手元でビルドするので、Cloud Build は使いません。サービスは限定公開にし、最大インスタンス数を 1 にします。最後にサービス・リポジトリ・サービス アカウントを削除します

手順1. API を有効にする

gcloud services enable run.googleapis.com artifactregistry.googleapis.com

手順2. Artifact Registry のリポジトリを作る

このあとのコマンドで使う値を、シェルの変数に入れておきます（ターミナルを開き直したら、もう一度実行します）。

REGION=asia-northeast1
PROJECT_ID=$(gcloud config get-value project)
REPO=study-repo
IMAGE=$REGION-docker.pkg.dev/$PROJECT_ID/$REPO/hello:v1

gcloud artifacts repositories create $REPO \
  --repository-format=docker \
  --location=$REGION \
  --description="study"

gcloud artifacts repositories list --location=$REGION

手順3. アプリを用意する

作業用のディレクトリ（例：hello）を作り、次の2つのファイルを置きます。Python の標準ライブラリだけで書いた、JSON を返す小さな Web サーバーです。

app.py

import json
import os
import signal
import sys
from http.server import BaseHTTPRequestHandler, HTTPServer


class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        body = {
            "message": os.environ.get("MESSAGE", "hello"),
            "revision": os.environ.get("K_REVISION", "local"),
        }
        data = (json.dumps(body, ensure_ascii=False) + "\n").encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json; charset=utf-8")
        self.end_headers()
        self.wfile.write(data)
        print(f"GET {self.path} -> 200", flush=True)  # 標準出力は Cloud Logging に送られる

    def log_message(self, format, *args):
        pass  # 既定のアクセスログ（標準エラー出力）は出さない


# Cloud Run はインスタンスを止める前に SIGTERM を送る
signal.signal(signal.SIGTERM, lambda signum, frame: sys.exit(0))

port = int(os.environ.get("PORT", "8080"))  # Cloud Run が PORT 環境変数で待ち受けるポートを渡す
HTTPServer(("", port), Handler).serve_forever()

Dockerfile

FROM python:3.12-slim
WORKDIR /app
COPY app.py .
CMD ["python", "app.py"]
  • PORT：Cloud Run は、コンテナが待ち受けるポートを PORT 環境変数で渡します（既定は 8080）。待ち受けるアドレスは 0.0.0.0 にする必要があります（127.0.0.1 では届かない）。HTTPServer(("", port), …) の "" は 0.0.0.0 と同じ意味です
  • K_REVISION：Cloud Run が設定する環境変数で、いま動いているリビジョンの名前が入ります。どのリビジョンが応答したかを確かめるために返しています
  • MESSAGE：デプロイのときに自分で設定する環境変数です

手順4. ビルドして push する

# hello ディレクトリで実行する
# Docker の設定に、Artifact Registry の認証を gcloud に任せる設定を追加する（1回だけ）
gcloud auth configure-docker $REGION-docker.pkg.dev

# ① ビルド（Cloud Run 用に linux/amd64 を指定する）
docker build --platform linux/amd64 -t $IMAGE .

# （任意）手元で動かしてみる。別のターミナルで curl localhost:8080 を実行し、Ctrl+C で止める
docker run --rm -p 8080:8080 -e MESSAGE=local $IMAGE

# ② push
docker push $IMAGE

# リポジトリに入ったことを確認する
gcloud artifacts docker images list $REGION-docker.pkg.dev/$PROJECT_ID/$REPO --include-tags

手順5. サービス ID 用のサービス アカウントを作る

gcloud iam service-accounts create hello-run-sa --display-name="hello Cloud Run service"
SA=hello-run-sa@$PROJECT_ID.iam.gserviceaccount.com

このアプリは Google Cloud の API を呼ばないので、ロールは付けません。

手順6. ③ デプロイする（限定公開サービス）

gcloud run deploy hello \
  --image=$IMAGE \
  --region=$REGION \
  --service-account=$SA \
  --no-allow-unauthenticated \
  --max-instances=1 \
  --set-env-vars=MESSAGE=v1
指定意味
--image手順4で push したイメージ
--regionCloud Run のサービスはリージョンのリソース。リポジトリと同じ東京にする
--service-accountサービス ID。指定しないと、Compute Engine のデフォルト サービス アカウントになる
--no-allow-unauthenticated限定公開サービスにする（allUsers に roles/run.invoker を付けない）
--max-instancesインスタンスを最大 1 台にする（料金の上限のため）
--set-env-vars環境変数 MESSAGE を設定する。--set-env-vars は、ここに書かなかった既存の環境変数を消す（手順8では、既存を残す --update-env-vars を使う）

手順7. 呼んでみる

URL=$(gcloud run services describe hello --region=$REGION --format="value(status.url)")
echo $URL

# トークンなし：403 が返る
curl -s -o /dev/null -w "%{http_code}\n" $URL

# ID トークン付き：応答が返る（トークンの有効期間は1時間）
TOKEN=$(gcloud auth print-identity-token)
curl -H "Authorization: Bearer $TOKEN" $URL

自分のアカウントはプロジェクトのオーナーなので、roles/run.invoker の権限も持っています。gcloud auth print-identity-token で作ったトークンは、開発中に試すためのものです。アプリからほかのサービスを呼ぶときは、サービス ID のトークンを使います。

手順8. 新しいリビジョンを、トラフィックを流さずにデプロイする

# 環境変数だけを変える（--update-env-vars はほかの環境変数を残す）。設定を変えても新しいリビジョンができる
gcloud run services update hello --region=$REGION \
  --update-env-vars=MESSAGE=v2 \
  --no-traffic \
  --tag=green

# リビジョンが2つになった
gcloud run revisions list --service=hello --region=$REGION

# トラフィックの割り当て（新しいリビジョンは 0%、タグ green の URL がある）
gcloud run services describe hello --region=$REGION --format="yaml(status.traffic)"

# サービスの URL は v1 のまま
curl -H "Authorization: Bearer $TOKEN" $URL

# タグの URL（上の status.traffic の url）だと v2 が返る
curl -H "Authorization: Bearer $TOKEN" https://green---…（上でコピーした URL）

手順9. 半分ずつ流してから、全部切り替える

# タグ green のリビジョンに 50%
gcloud run services update-traffic hello --region=$REGION --to-tags=green=50

# 何回か呼ぶと、v1 と v2 が混ざって返る
for i in 1 2 3 4 5 6; do curl -s -H "Authorization: Bearer $TOKEN" $URL; done

# 最新のリビジョンに 100%（今後のデプロイでも、最新のリビジョンに自動で移る状態に戻る）
gcloud run services update-traffic hello --region=$REGION --to-latest
curl -H "Authorization: Bearer $TOKEN" $URL

手順10. ロールバックする

# 1つ目のリビジョンの名前（hello-00001-xxx）を確認する
gcloud run revisions list --service=hello --region=$REGION

# 1つ目のリビジョンに 100% を戻す（名前は上で確認したものに置き換える）
gcloud run services update-traffic hello --region=$REGION --to-revisions=hello-00001-xxx=100
curl -H "Authorization: Bearer $TOKEN" $URL

手順11. ログを見る

gcloud run services logs read hello --region=$REGION --limit=10

アプリが標準出力に書いた GET / -> 200 が、Cloud Logging に送られています。

手順12. 片付ける

gcloud run services delete hello --region=$REGION
gcloud artifacts repositories delete $REPO --location=$REGION
gcloud iam service-accounts delete $SA

# 手元のイメージも消す
docker rmi $IMAGE

# 残っていないことを確認する（Listed 0 items.）
gcloud run services list
gcloud artifacts repositories list

リポジトリを削除すると、中のイメージも一緒に削除されます。有効にした API はそのままで構いません（有効にしているだけでは料金はかかりません）。

Q1. 手順7で、トークンを付けないと 403 が返ったのはなぜでしょう？誰でも呼べるようにするには、どうすればよいでしょう？

答えを見る

--no-allow-unauthenticated でデプロイしたので、roles/run.invoker を持つプリンシパルしか呼べないからです。トークンがないと、誰からのリクエストか判断できません。誰でも呼べるようにするには、Cloud Run 起動元の IAM チェックを無効にする（--no-invoker-iam-check。公式の推奨）か、allUsers に roles/run.invoker を付与します（--allow-unauthenticated）。

Q2. 手順8では、イメージを変えずに環境変数だけを変えました。それでも新しいリビジョンができたのはなぜでしょう？

答えを見る

リビジョンは、イメージと設定の組で、作った後は変更できないからです。環境変数などの設定を変えると、新しいリビジョンになります。そのおかげで、手順10のように、設定の変更も前のリビジョンに戻すだけで元に戻せます。

Q3. 手順4で --platform linux/amd64 を付けなかったら、どうなるでしょう？（Apple シリコンの Mac の場合）

答えを見る

linux/arm64 用のイメージができます。push はできますが、Cloud Run のコンテナは Linux 64 ビット（x86_64）用である必要があるので、期待どおりに動きません。--platform linux/amd64 を付けてビルドし直すか、Cloud Build でビルドします。

7. 確認テスト（ACE 形式）

問1. Cloud Run で動いている Web アプリの新しいバージョンをリリースします。まず利用者の 10% だけに新しいバージョンを使ってもらい、問題がなければ全員に広げたいと考えています。どうすればよいですか。

  1. 新しいバージョンを別の Cloud Run サービスとしてデプロイし、利用者に新しい URL を案内する
  2. 新しいバージョンを --no-traffic を付けてデプロイし、gcloud run services update-traffic で新しいリビジョンに 10% を割り当てる
  3. 新しいバージョンをそのままデプロイし、最大インスタンス数を 10% に減らす
  4. 新しいバージョンを Compute Engine の VM にデプロイし、ロードバランサで 10% を振り分ける
答えを見る

正解：B

Cloud Run は、リビジョンごとにトラフィックの割合を指定できます。--no-traffic でデプロイすれば、新しいリビジョンにはまだトラフィックが流れないので、そこから割合を少しずつ増やせます。

  • A：利用者に URL を変えてもらう必要があり、割合も制御できません
  • C：そのままデプロイすると、すべてのトラフィックが新しいリビジョンに移ります。最大インスタンス数は台数の上限で、トラフィックの割合ではありません
  • D：Cloud Run の機能で実現できることに、余計な運用を増やします

問2. Cloud Run の新しいリビジョンに 100% のトラフィックを切り替えたところ、エラーが急増しました。できるだけ早く元の状態に戻したいと考えています。どうすればよいですか。

  1. 前のバージョンのソースコードからイメージをビルドし直し、デプロイする
  2. 新しいリビジョンの最小インスタンス数を 0 にする
  3. gcloud run services update-traffic で、前のリビジョンに 100% を割り当てる
  4. サービスを削除し、前のバージョンのイメージで作り直す
答えを見る

正解：C

前のリビジョンは残っているので、トラフィックの割り当てを変えるだけで、すぐに戻せます。

  • A：ビルドとデプロイに時間がかかります
  • B：最小インスタンス数は待機させておく台数の設定で、どのリビジョンにトラフィックを流すかは変わりません
  • D：URL が変わる可能性があり、時間もかかります

問3. Cloud Run のサービス A を、同じプロジェクトにある Cloud Run のサービス B からだけ呼べるようにしたいと考えています。インターネットの誰からでも呼べる状態にはしたくありません。どうすればよいですか。

  1. サービス A を --allow-unauthenticated でデプロイし、URL をサービス B にだけ教える
  2. サービス A を --no-allow-unauthenticated でデプロイし、サービス B のサービス ID に、サービス A に対する roles/run.invoker を付与する
  3. サービス B のサービス ID に、プロジェクトの roles/run.admin を付与する
  4. サービス A のサービス ID に、サービス B に対する roles/run.invoker を付与する
答えを見る

正解：B

サービスを呼べるかどうかは、呼ばれる側（サービス A）の許可ポリシーで、呼ぶ側（サービス B のサービス ID）に roles/run.invoker があるかで決まります。

  • A：URL を知っていれば誰でも呼べてしまいます
  • C：呼べるようにはなりますが、サービスの作成や削除までできてしまい、最小権限ではありません
  • D：向きが逆です。これはサービス A がサービス B を呼べるようにする設定です

問4. Cloud Run のサービスから、Cloud Storage のバケットにあるファイルを読み取ります。最小権限の原則に従いたいと考えています。どうすればよいですか。

  1. サービスのサービス ID は指定せず、Compute Engine のデフォルト サービス アカウントを使う
  2. サービス アカウント キーを作成してコンテナ イメージに含め、アプリから読み込む
  3. 専用のサービス アカウントを作り、そのバケットに対する roles/storage.objectViewer を付与して、サービスのサービス ID に指定する
  4. バケットの allUsers に roles/storage.objectViewer を付与する
答えを見る

正解：C

サービスが API を呼ぶときは、サービス ID の権限を使います。専用のサービス アカウントに、必要なバケットの読み取りロールだけを付けるのが最小権限です。

  • A：デフォルト サービス アカウントには編集者ロールが付いていることがあり、権限が大きすぎます
  • B：キーが漏れる危険があります。Cloud Run ではキーは不要です
  • D：インターネットの誰でもファイルを読めてしまいます

問5. Cloud Run の API は、夜間はリクエストがほとんどありません。朝の最初のリクエストだけ応答が数秒遅いという苦情があります。どうすればよいですか。

  1. 最大インスタンス数を増やす
  2. 最小インスタンス数を 1 以上にする
  3. 1つのインスタンスが同時に処理するリクエストの数を増やす
  4. サービスを別のリージョンにデプロイし直す
答えを見る

正解：B

リクエストがない間にインスタンスが 0 台まで減り、最初のリクエストでインスタンスの起動を待っている（コールド スタート）と考えられます。最小インスタンス数を 1 以上にすると、起動したインスタンスが残ります。ただし、その分の料金がかかり続けます。

  • A：上限を上げても、0 台から起動する遅れはなくなりません
  • C：インスタンスが動いているときの処理の量は変わりますが、0 台からの起動の遅れはなくなりません
  • D：リージョンを変えても、コールド スタートは起きます

問6. 開発チームが、手元で作ったコンテナ イメージを Cloud Run にデプロイしたいと考えています。Google Cloud の推奨に従って、イメージをどこに置けばよいですか。

  1. Container Registry（gcr.io）
  2. Cloud Storage のバケットに、イメージを tar ファイルとして保存する
  3. Cloud Run と同じリージョンにある、Artifact Registry の Docker 形式のリポジトリ
  4. Compute Engine の VM のディスク
答えを見る

正解：C

コンテナ イメージは Artifact Registry に置きます。Cloud Run と同じリージョンにすると、イメージの取り出しが速く、ネットワークの料金もかかりません。

  • A：Container Registry は 2025 年 3 月 18 日にシャットダウンされ、イメージを書き込めません
  • B、D：Cloud Run には、コンテナ レジストリにあるイメージを指定してデプロイします。バケットの tar ファイルや VM のディスクは指定できません

まとめ

  • ソースコード →（①ビルド）→ コンテナ イメージ →（②push）→ Artifact Registry →（③デプロイ）→ Cloud Run サービス。Apple シリコンの Mac では linux/amd64 でビルドする
  • サービスの中に、変更できないリビジョンが積み重なる。トラフィックはリビジョンごとに割合で割り当てられ、--no-traffic とタグで段階的に切り替え、前のリビジョンに戻してロールバックできる
  • インスタンスはリクエストに応じて増減し、既定では 0 台まで減る。コールド スタートが気になるなら最小インスタンス数、上限は最大インスタンス数
  • 誰が呼べるかは roles/run.invoker（公開するなら IAM チェックの無効化か allUsers）と、ネットワーク上り（内向き）の設定。サービスが何をできるかはサービス ID。サービス ID には専用のサービス アカウントを使う
